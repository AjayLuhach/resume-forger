How It Works

Resume Forge is a self-hosted, single-user job-application toolkit — one server, one MongoDB, three flows: tailor a resume to a JD, run an outreach pipeline against scraped LinkedIn posts, and track direct applications. Your resume, settings and every row you triage live in your own database. Optionally, peers' databases feed you the jobs they have already scraped and analyzed.

1
Getting Started
Clone, configure, create your user, and log in
1
Clone & install
Run npm install. PDF conversion uses LibreOffice — npm run install-pdf apt-installs it on Linux; otherwise the pipeline falls back to Puppeteer/Chrome.
2
Configure .env
Copy .env.example → .env. Fill in AI provider creds (Bedrock or Gemini), MONGO_URI, MONGO_DB, and SESSION_SECRET (generate via openssl rand -hex 32). User identity is not an env concern — only infrastructure goes here.
3
Start the server
npm run web → http://localhost:<PORT> (the PORT in .env; 5003 by default — if you change it, set the same number under Server port in the extension popup). With an empty users collection every page redirects to /setup until a user exists.
4
Create your user (first run)
/setup is a one-time form — name, email, password — that creates the user and logs you in. The terminal equivalent is node scripts/create-user.js --username "Jane Doe" --email jane@example.com (without --password a random password is generated and printed once — copy it, then change it under Settings). Either path writes the auth doc to users and creates the user's compound index on job_tracker so the apply tracker is fast from day one. The database holds exactly one user — a second is refused.
5
Add your resume
Open Resume and paste your tailor JSON (the deep version) and feed JSON (the slim version used for outreach scoring). Upload your master PDF. Everything lives in mongo at users.<you>.{data,feedData,pdf}.
2
How Identity Works
MongoDB is the single source of truth — no env, no file fallback

The users collection holds exactly one document — you — keyed by username. Every flow resolves that user from the session, or falls back to the sole user when there is no session (CLIs, the extension's bearer-token path) — never from environment variables, never from a local file, never from a query parameter.

What's on each user doc

  • username — canonical name (e.g. "Jane Doe"). Doc key.
  • auth.email + auth.passwordHash — login credentials.
  • data — tailor-side resume JSON (deep). 5-deep history ring on every save.
  • feedData — feed-side resume JSON (slim), including preferences (country, currency, salary floor, reject rules). Used by the outreach scorer/drafter.
  • pdf — master resume PDF as BSON Binary.
  • emailConfig.smtp — your SMTP creds, set under Settings. Needed before Generate emails / Send approved will run.

Who's the active user?

  • Web requests — the signed session cookie, else the sole user in the database. There is no per-request user override.
  • CLIs (scripts/feed/feed-cli.js, scripts/feed/send-emails.js) — --user "Name" is optional; without it the sole user is used. With zero or more than one user the CLI stops with an error rather than guessing.
Removed patterns (do not reintroduce): identity from env vars (RESUME_USER et al.), identity from a local resumeData.json, nickname maps, module-init globals that pre-bind to one user, per-request query / body user overrides, and a join-date visibility cutoff. See CLAUDE.md for the full anti-pattern list.
3
The Three Flows
Tailor, Outreach, Direct apply — what each does end-to-end
Tailor — paste a JD, get an ATS-tuned PDF
1
Pre-flight checks
Verifies AI provider creds, that template.docx exists, and tests LibreOffice availability.
2
Validate JD & load resume
JD needs ≥ 100 chars. Resume data is loaded from users.<you>.data in mongo — validated against the schema before the AI sees it.
3
AI rewrite + emails + DM
The provider extracts JD keywords, matches them against your skills, and rewrites your title, summary, bullets, skills, and project descriptions to maximize keyword alignment. It also drafts an application email and a LinkedIn DM.
4
ATS scoring
Deterministic scorer: keyword match %, title match, experience gap penalties, and hard-reject gates (e.g. JD demands Java but your stack is JavaScript). 70+ is good; 50–69 mid; <50 needs attention.
5
DOCX → PDF
Typesets the resume as HTML in Chrome and measures it so it fits one page (scaling first, trimming old roles only as a last resort); template.docx + LibreOffice is the fallback and the DOCX download. Saves <Name>_<Role>.pdf to OUTPUT_DIR (default ~/Downloads/resume-forge) and a row in resume_variants.
Outreach — LinkedIn posts → personalized emails
1
Parse
Paste LinkedIn post HTML/text (or use the parser) → output/extract.json. Click Add posts on the Posts tab to do this from the UI.
2
Generate
AI extracts who's hiring, what role, what skills, what salary → posts collection (the post pool, deduplicated by postId).
3
Score & draft emails
Score every post against your feedData (experience, salary, skills with aliases, cannotClaim list, preferences). Posts that pass thresholds become drafted emails in user_emails. Click Generate emails on the Feed tab — it first checks that a feed resume and SMTP settings exist and points you to the right page if either is missing.
4
Review & approve
Drafted emails show on Feed. Approve / reject / fix from the UI. Approving doesn't send — that's still a manual click.
5
Send via your SMTP
Send approved sends every approved-unsent email using the emailConfig.smtp on your user doc, set under Settings.
Direct apply — job tracker

The Apply board lists every job the extension has analyzed, plus any pulled in from peers. Each carries your status (Pending / Applied / Interviewing / Success / Rejected). Paste a job URL or post to add. The user's compound index (apply_<Name>_1) on job_tracker keeps reads ~80 ms warm.

Capture LinkedIn job searches through the extension: save search URLs, hit Open & capture (or click Start capturing and browse a search yourself), then Load captured — the server extracts the job IDs, tags each NEW / SCANNED / IMPORTED / BLOCKED, and Open batch opens the new ones in tabs so the extension analyzes each. Peer Job Sources
Pull jobs friends have already scraped and analyzed — triage without re-scraping

Everyone runs their own copy of Resume Forge against their own database. If a friend agrees to share, paste their MongoDB connection string under Settings → Peer job sources. Peers live in data/peers.json on your machine — a local, gitignored file, never your database — so a connection string someone trusts you with is only ever readable by you.

  • Every 30 s the server reads each peer's job_tracker and upserts the rows you don't have as pending rows in your own database, analysis attached. Test and Sync now on the Settings page run a single peer on demand.
  • Imported rows carry importedFrom ({ peerId, label, at, peerJobLink, peerAnalyzedAt, peerRowStatus }) and show an imported pill on Apply and an IMPORTED tag on the Scanner. Their verdict and score are the peer's — scored against the peer's resume, not yours.
  • Re-analyze runs the scanner's analysis over an imported row with your own resume and replaces the peer's verdict; opening the job with the extension running does the same automatically. Once re-analyzed the row is yours and the pill disappears.
  • Reject / apply from the Apply board as usual — your status never flows back to the peer. Removing a peer with purge also drops the rows it imported.
Read-only by design. The sync only ever reads from a peer's database and only ever writes to yours. When you share your own connection string, hand out a read-only database user.

Resume Data Shape
What lives in users.<you>.data and users.<you>.feedData

Your resume lives in mongo, edited via the Resume tab. Two shapes coexist:

Tailor-side (data) — deep, used by the Generate pipeline

  • personalInfo required — name, email required; phone/location/links optional.
  • meta required — experienceStart (e.g. "Aug 2023"), stack, optional cannotClaim, coreProjects, primaryCloud.
  • professionalSummary.default required — 200+ char summary, rewritten per JD.
  • skills required — categorized buckets (frontend / backend / toolsDevOps / databases / other), each an array of skill strings. The labels are web-flavoured but any discipline maps onto them; other is the catch-all.
  • experience required — array of jobs; each needs company, title, duration. May nest projects[] and bullets[].
  • projects required — personal projects. Detailed descriptions = better AI rewrites.
  • education optional — array; needs degree + institution.

Feed-side (feedData) — slim, used by the outreach scorer

  • personalInfo — including currentCTC + expectedCTC for the email sign-off block.
  • experienceStart, stack, summary.
  • skills — same map shape; alias-aware matching against post requirements.
  • cannotClaim — skills the email drafter must never claim on your behalf: the technologies adjacent to your stack that recruiters ask for but you have not used.
  • projects — thin list of personal projects.
  • preferences — country, currency and salary unit, USD rate, salary floor, allowed experience gap, walk-in / contract / intern / staffing rejects, excluded companies, notice period. Defaults are India / INR / LPA; the feed example on the Resume page lists every key with its default.

Loading in code

// Tailor side
import config from './config.js';
const candidate = await config.loadCandidate(username);

// Feed side
import { loadCandidate } from './services/feed/feed-config.js';
const candidate = await loadCandidate(username);
// → feedData if set, else falls back to data
Validation — on each request to /api/validate-resume, the server reads users.<you>.data from mongo and runs the schema check in services/resume-validator.js. The Generate page shows the result in a banner (green / amber / red).

AI Providers
Bedrock + Gemini, plus how to add your own

AWS Bedrock (default)

  • AI_PROVIDER=bedrock in .env
  • Needs BEDROCK_API_KEY (bearer key for the mantle endpoint) — no AWS/IAM credentials
  • BEDROCK_BASE_URL picks the region; default is ap-south-1 (Mumbai)
  • BEDROCK_MODEL takes an alias (deepseek, mistral, glm, qwen, gemma) or a full mantle model ID
  • The model catalogue depends on the region — ap-south-1 is open-weight only; us-east-1 also lists Anthropic and OpenAI models, subject to account entitlement
  • Feed pipeline (scoring + drafting) uses BEDROCK_MODEL_ID independently (e.g. Gemma 3 27B)
  • Scanner uses SCANNER_MODEL_ID (default gemma)

Google Gemini

  • AI_PROVIDER=gemini
  • Needs GEMINI_API_KEY
  • Auto-rotates through the model pool on rate limits; free tier works for low volume

Custom provider

  • Drop a file in services/providers/ extending BaseProvider
  • Implement tailorResume(jd, resumeData)
  • Register in services/providers/registry.js
  • See services/providers/README.md for the full contract

CLI & Claude Code
Terminal commands; the UI shells out to most of these internally

npm scripts

npm run web              # main server on PORT from .env (5003 by default)
npm run install-pdf      # apt-install libreoffice-writer
npm run models           # list available Bedrock models
npm run feed:send        # send approved emails (--user optional, see below)

Feed pipeline (terminal)

node scripts/feed/feed-cli.js parse [--file path]          # clipboard → output/extract.json
node scripts/feed/feed-cli.js generate [--user "Name"]      # extract.json → posts collection
node scripts/feed/feed-cli.js emails   [--user "Name"]      # score + draft → user_emails
                          [--redraft]
node scripts/feed/feed-cli.js send     [--user "Name"]      # list approved unsent

# --user is optional on every CLI: with one user in the database it is
# inferred; with zero or several the command stops with an error.

One-off scripts

node scripts/create-user.js --username "X" --email x@y.com [--password ...]
node scripts/create-user.js --password "new-password"                 # reset the existing user's password
                                                # terminal alternative to /setup; refuses a second user
node scripts/ensure-indexes.js                  # every index, idempotent — safe on a fresh database
node scripts/seed-local-from-remote.js --user "X" --apply --drop
                                                # copy your slice into a local test database
node scripts/dump-mirrors.js                    # rebuild the mirror snapshots in one pass
node scripts/list-bedrock-models.js

Mongo Collections
Quick map of what's stored where
  • users — exactly one doc: you. Keyed by username. Carries auth, data, feedData (with preferences), pdf, SMTP creds. Index: username (unique).
  • posts — the LinkedIn-scrape pool. Indexes: postId, status, job.salaryMinLPA, _companyKey.
  • user_emails — email drafts (statuses: no_email, drafted, approved, rejected, sent). Indexes: (username, postId), (username, status), more.
  • user_connects — connection requests queued from DM-only posts (invited → connected → messaged); acceptance is detected when the profile shows up in a connections scrape.
  • connections — your LinkedIn connections, scraped by the extension, matched to tracked jobs by company.
  • job_tracker — apply-tracker rows: everything the extension analyzed plus rows pulled from peers (importedFrom set until you re-analyze them). Indexes: jobLink (unique), createdAt, plus the user's compound apply_<Name>_1, created by /setup / create-user.js.
  • resume_variants — every tailored resume ever generated. Indexes: (username, generatedAt), (username, jobCompany, jobTitle).
Indexes belong in scripts/ensure-indexes.js (idempotent, safe to run on a fresh database), not in services/db.js. Boot-time createIndex was removed to avoid racing with a collection rename — don't add it back. The user's own job_tracker index is created when the account is created.
